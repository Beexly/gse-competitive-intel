Technical API Questions

The recommended pattern:

1. Bootstrap once with a narrow snapshot
Call GET /api/v2/sports/{sport_id}/events/{date}?market_ids=1,2,3,41,42,43&affiliate_ids=3,19,23&main_line=true&hide_closed=true to load open main-line moneyline, spread, and total prices.

2. On delayed plans, poll narrow snapshots
Delayed or unknown plans should repeat the narrowest snapshot that fits the use case at an appropriate cadence. Every successful snapshot bills the rows it returns.

3. On zero-delay plans, poll market deltas
Use market deltas only when you have a known zero-delay entitlement, the bootstrap response explicitly returns X-Data-Delay-Seconds: 0, and body meta.delta_last_id is a valid positive integer (as a number or numeric string). Pass that cursor to GET /api/v2/markets/delta?last_id=…&sport_id=4&market_ids=1,2,3,41,42,43&affiliate_ids=3,19,23. Delta filters are literal, so include live market IDs 41, 42, and 43 with the same sport and book scope. Apply each row's is_main_line and closed_at values, and save the cursor from each successful delta page. If any requirement is absent or invalid, repeat narrow snapshots. Read the Efficient Polling guide.

4. Or use WebSocket on Ultra+
Ultra+ can use the multiplexed WebSocket stream for a server-side connection. Use a scoped WebSocket snapshot or a REST baseline, then apply live updates and refresh state after reconnecting.
Ultra+ plans can connect a server to wss://therundown.io/api/v2/ws. Authenticate with an X-TheRundown-Key header sourced from your environment.

Subscribe explicitly to markets, scores, plays, or live. Request snapshot: true in the subscription parameters, bounded by event_ids or sport_ids plus date; the plays channel requires event_ids.

The stream sends snapshot frames, then snapshot_complete, then deltas. An existing subscription can request a fresh snapshot with action: snapshot.

The dedicated /ws/markets endpoint is for odds updates only. Filter it by market_ids, affiliate_ids, and event_ids; each market_price frame carries one changed price row. Keep a REST baseline and use it for recovery. Read the multiplexed WebSocket guide.
One odds data point is one returned price row: participant or outcome × line or value × sportsbook. Missing prices are not charged. Additional participants, alternate lines, and sportsbooks each add returned rows. Examples:

• GET /api/v2/events/{id}?market_ids=1&affiliate_ids=3&main_line=true&hide_closed=true — a two-sided moneyline normally returns two participant price rows = 2 odds data points, plus the response's event/score/live-state rows
• GET /api/v2/events/{id}?market_ids=1,2,3&affiliate_ids=3,19,23&main_line=true&hide_closed=true — six main-line participant/outcome rows × three books = up to 18 odds data points when every price is available, plus event/score/live-state rows

Every successful 200 snapshot bills the price rows it returns, even when a price is unchanged. V2 event snapshot responses also add one event datapoint per event, one score datapoint when present, and one more score-category datapoint when live game state is present. Delayed plans should repeat narrow filtered snapshots at the cadence their use case needs. On a zero-delay plan, use /api/v2/markets/delta only when the account has a known zero-delay entitlement, the bootstrap response explicitly returns X-Data-Delay-Seconds: 0, and meta.delta_last_id is a valid positive integer (as a number or numeric string). Otherwise, repeat a narrow filtered snapshot. Each changed price row is one odds point. X-Datapoints is authoritative for the billed total on billed responses. X-Datapoints-Breakdown is optional, is not currently emitted by /api/v2/markets/delta. WebSocket price-row messages count as one point each. Reference data (/sports, /affiliates, and /markets) is always free.
The /api/v2/markets/delta endpoint returns only price rows that changed since your cursor and is the polling pattern for zero-delay plans only. Use it only with a known zero-delay entitlement and an explicit X-Data-Delay-Seconds: 0 response header. Starter and other delayed plans should use narrow snapshots instead; a body cursor from a delayed snapshot can skip rows. Zero-delay flow:

1. Bootstrap once with a filtered zero-delay snapshot. Include every literal market ID you need, including live IDs 41, 42, and 43: GET /api/v2/sports/4/events/{date}?market_ids=1,2,3,41,42,43&affiliate_ids=3,19,23&main_line=true&hide_closed=true
2. Confirm X-Data-Delay-Seconds: 0 and read a valid positive integer cursor (as a number or numeric string) from meta.delta_last_id. Otherwise, repeat filtered snapshots.
3. Poll with the same sport, market, and book filters: GET /api/v2/markets/delta?last_id=…&sport_id=4&market_ids=1,2,3,41,42,43&affiliate_ids=3,19,23
4. Save the next cursor and continue while meta.has_more is true

Each delta entry is one changed participant/line/book price row and one odds data point. Apply its is_main_line and closed_at fields client-side. If the cursor is stale and returns 400, re-bootstrap once and resume from the new cursor.
A value of 0.0001 is our sentinel for "off the board" — the sportsbook removed this line. It applies to:

• Moneylines, spreads, and totals
• Player and team props
• Both pre-match and in-play markets

How to handle it: In your code, treat 0.0001 as null/unavailable. Display "OFF" or hide the line. On zero-delay plans, /api/v2/markets/delta notifies you when a line is taken down. On delayed plans, refresh your filtered snapshot at the cadence your use case needs.
V2 is our normalized market schema that provides a unified structure across published sportsbook sources. Instead of the legacy per-book V1 format, V2 gives you:

• 550+ market types — moneylines, spreads, totals, player props, team totals, futures, and more
• Consistent structure — every market follows the same participant/line/price schema regardless of sportsbook
• Supported periods — prematch, halves, quarters, and live in-play markets where available

Access V2 data via the /api/v2/ endpoints. Use /api/v2/events/{eventID}/markets for event odds and /api/v2/markets for the full catalog of market definitions.
